## Ringkasan

Portal tracking OpRec punya tiga mutation setelah sesi tracking didapat:
`PUT /recruitment/track` (update data + unggah berkas), `POST /recruitment/track/correction`
(membuat permintaan koreksi + activity log + queue email ke staff), dan
`POST /recruitment/track/feedback` (menulis penilaian). Ketiganya berada di grup
middleware `recruitment.tracking.session` **tanpa limiter**; hanya
`POST /recruitment/track` (authenticate) yang memakai `throttle:oprec-track`.

Perbaikan: tiga named limiter terpisah, dipasang pada route-nya, dengan kunci
identitas sesi tracking (id aplikasi) dan fallback IP. Kuota tiap pendaftar
terpisah, sehingga pendaftar di belakang NAT yang sama tidak saling memblokir.

## Akar masalah (sebelum)

```php
// routes/web/oprec.php (sebelum)
Route::middleware('recruitment.tracking.session')->group(function (): void {
    Route::put('/track', [TrackingController::class, 'update'])->name('track.update');
    Route::post('/track/correction', [CorrectionRequestController::class, 'store'])->name('track.correction');
    Route::post('/track/feedback', [FeedbackController::class, 'store'])->name('track.feedback.store');
});
```

Tidak ada limiter dan tidak ada pembatasan frekuensi di controller/service:

- `TrackingController::update()` memanggil `ApplicationEditor::update()` (tulis
  beberapa tabel + `Storage::disk('local')` untuk berkas).
- `CorrectionRequestService::store()` menulis baris koreksi, activity log, dan
  `SendRecruitmentCorrectionRequestStaffJob::dispatch(...)->afterCommit()`
  (email ke staff).
- `FeedbackService::submit()` menulis baris feedback.

Gate domain (`ApplicationEditGate`, `FeedbackService::canSubmit`) memang
membatasi hasil akhir, tetapi tidak membatasi **laju request**: request tetap
masuk, tetap query DB, tetap menjalankan validasi/IO, dan job email tetap
dibuat pada percobaan pertama tiap jendela.

## Keputusan desain

| Keputusan | Alasan / alternatif yang ditolak |
| --- | --- |
| Tiga named limiter terpisah: `oprec-track-update`, `oprec-track-correction`, `oprec-track-feedback` | Biaya tiap endpoint berbeda (upload vs email job vs insert). Satu limiter gabungan akan membuat edit yang sah menghabiskan kuota koreksi/feedback. Ini juga rekomendasi audit §`BE-P1-006`. |
| Kunci = id aplikasi tracking dari sesi; fallback IP bila sesi belum/tidak valid | Sesi tracking adalah identitas pendaftar (guest tanpa akun). Menggabung IP **ke dalam** kunci (`appId|ip`) justru bisa di-reset dengan rotasi IP, dan pola `user id ?: ip` sudah dipakai limiter `scan-*` di repo ini. Fallback IP tetap membatasi flood sebelum guard sesi berjalan karena `ThrottleRequests` diproses lebih dulu (lihat catatan urutan). |
| Nilai batas di `config/recruitment.php` dengan env (`RECRUITMENT_TRACK_*_RATE_LIMIT`) | Aturan softcoded: angka tidak tersebar di route. Default `update=12/menit`, `correction=5/menit`, `feedback=5/menit`. |
| Batas menit tunggal, bukan window panjang | Gate domain sudah membatasi hasil (satu koreksi aktif, satu feedback). Yang perlu dibatasi adalah burst; window panjang tanpa kebutuhan akan memblokir user normal saat edit berulang. |
| Tidak mengubah frontend | Handler 429 global sudah ada (`useGlobalHttpStatusToast` + `lib/http-retry-after.ts`), dan `bootstrap/app.php` sudah menyalin `Retry-After` ke respons Inertia. Perubahan frontend akan menduplikasi perilaku yang sudah bekerja. |
| `throttle` dipasang per route, bukan di group | `GET /track/dashboard`, `GET /track/edit`, dan `POST /track/logout` tetap bebas; tiket hanya menyebut mutation. |

**Urutan middleware (penting untuk kunci).** `Illuminate\Routing\Middleware\ThrottleRequests`
ada di `$middlewarePriority` Laravel, setelah `StartSession` dan sebelum
`SubstituteBindings`/`Authorize`; `EnsureTrackingSession` tidak ada di daftar
prioritas. Hasilnya limiter berjalan sebelum guard sesi, tetapi sesi (dan id
aplikasi) sudah tersedia. Inilah sebabnya fallback IP benar-benar terpakai untuk
request tanpa sesi — dibuktikan test `test_requests_without_tracking_session_fall_back_to_ip_limit`.

## Perilaku sebelum vs sesudah

| Skenario | Sebelum | Sesudah |
| --- | --- | --- |
| `PUT /track` diulang terus oleh satu sesi | Semua diproses (tulis DB + IO) | 12 request/menit; request ke-13 → `429` + `Retry-After`, data tidak berubah |
| `POST /track/correction` diulang | Percobaan pertama membuat baris + job email; sisanya ditolak gate domain tapi tetap query DB | 5 request/menit; percobaan ke-6 → `429` sebelum controller |
| `POST /track/feedback` diulang | Idem (gate domain menolak, request tetap diproses) | 5 request/menit; percobaan ke-6 → `429` sebelum controller |
| Dua pendaftar di IP sama (NAT kantor) | — | Kuota terpisah per id aplikasi; salah satu terkena 429 tidak memblokir yang lain |
| Request tanpa sesi tracking | Redirect ke login, tetap satu query `find()` per request | Setelah kuota IP habis → `429`; flood tidak lagi menembus guard sesi |
| User normal mengedit beberapa kali | Tetap jalan | Tetap jalan (12/menit) |

### Cakupan test

Catatan: repo ini belum punya runner unit test frontend (FE-AUDIT-002), jadi
validasi UI memakai E2E browser; sisi backend memakai feature test (test class
PHPUnit, bukan unit test murni, karena alur terikat HTTP + database).

Feature (`tests/Feature/Recruitment/RecruitmentTrackingMutationThrottleTest.php`):

1. `update` → 429 pada request ke-(limit+1) **dan** `full_name` tetap nilai
   dari request sukses terakhir (429 tidak menyimpan data).
2. `correction` → 429 pada request ke-(limit+1); gate domain tetap menjaga
   hanya satu baris koreksi.
3. `feedback` → 429 pada request ke-(limit+1); hanya satu baris feedback.
4. Isolasi sesi: sesi pertama habis → 429; sesi kedua (aplikasi lain, IP sama)
   tetap bisa menyimpan.
5. Tanpa sesi tracking: fallback IP tetap menghasilkan 429.
6. Tiga route benar-benar mendeklarasikan named limiter masing-masing
   (mencegah middleware hilang saat refactor).

E2E (`tests/e2e/recruitment-tracking-throttle.desktop.spec.ts`, browser nyata):

- Login portal tracking lewat UI (bukan menanam cookie sesi).
- Anomali 1: `phone` berisi `bukan-nomor` dan NIM berspasi → error validasi
  tampil pada field, bukan 500.
- Anomali 2: flood `PUT /recruitment/track` dari konteks browser → berhenti di
  `429`, header `Retry-After` ada, dua request 429 berurutan konsisten.
- Anomali 3: submit form lewat UI saat kuota habis → toast
  "Terlalu banyak …" muncul (bukan diam / modal mentah).
- Isolasi: context browser kedua (IP sama) login sebagai pendaftar lain dan
  berhasil menyimpan → redirect dashboard.
- `afterAll` menghapus seluruh baris fixture; diverifikasi 0 sisa untuk
  `applications`, `documents`, dan periode (termasuk yang soft-deleted).

Dua temuan saat menyiapkan E2E (dicatat agar tidak terulang):

- `RecruitmentPeriod` memakai `SoftDeletes`, sehingga `delete()` pada cleanup
  meninggalkan baris dengan slug yang sama dan `INSERT` berikutnya gagal
  (`recruitment_periods_slug_unique`). Cleanup sekarang memakai
  `withTrashed()->forceDelete()`.
- `php artisan tinker --execute` **tidak** memberikan exit code non-zero saat
  exception, jadi kegagalan fixture tidak terlihat oleh `execFileSync`. Spec
  sekarang memverifikasi hasil create (`assertFixturesExist()`) sebelum test
  berjalan.

Perintah E2E:

```bash
E2E_BASE_URL=http://localhost:3000 \
E2E_ADMIN_EMAIL=<seeded-admin> \
E2E_ADMIN_PASSWORD=<seeded-password> \
npx playwright test recruitment-tracking-throttle --project=chromium-desktop --no-deps --retries=0
```

Catatan environment: folder artefak `storage/app/e2e` dimiliki uid hasil
user-namespace podman, sehingga harness menulis dari host gagal `EACCES`.
Diperbaiki dengan `podman unshare chmod -R a+rwX storage/app/e2e`
(folder gitignored, bukan kode). Tidak ada perubahan source untuk ini.

## Acceptance criteria

- [x] Setiap mutation (update, correction, feedback) punya limiter.
- [x] Limiter dikunci per sesi tracking; fallback IP untuk request tanpa sesi.
- [x] Response 429 konsisten dan membawa `Retry-After`; UI menampilkan feedback.
- [x] Test memastikan limit bekerja dan tidak memblokir sesi/user normal.
- [x] Tidak ada perubahan perilaku untuk user yang wajar (edit berulang tetap jalan).

## Risiko, batasan, dan rollback

- **Angka batas adalah kebijakan, bukan hasil ukur.** Default dipilih dari pola
  pemakaian (edit manual ±beberapa kali/menit); nilai dapat disetel lewat env
  tanpa deploy kode. Jika operasional menemukan false positive, naikkan
  `RECRUITMENT_TRACK_UPDATE_RATE_LIMIT`.
- **Batas per menit** tidak mencegah spam berjarak (1 request/menit). Untuk
  koreksi/feedback, gate domain sudah membatasi hasil; untuk update, dampaknya
  hanya IO/DB pada aplikasi milik penyerang sendiri.
- **Rotasi sesi/aplikasi:** penyerang dengan banyak aplikasi valid punya banyak
  bucket. Aplikasi hanya bisa dibuat lewat `POST /recruitment` yang sudah
  dibatasi `throttle:oprec-apply` (5/menit per IP) dan aturan NIM unik per
  periode.
- **`STRESS_BYPASS_THROTTLE`** tetap bisa melewati limiter di non-production
  (`AppServiceProvider::boot`), sama seperti limiter lain; produksi tidak
  terpengaruh.
- **Rollback:** revert commit kode + test + dokumen. Tidak ada migration,
  schema, route name, atau dependency baru; perilaku kembali tanpa throttle.

## Temuan di luar scope (dicatat, tidak diubah)

- `EnsureTrackingSession` tetap menjalankan satu query `find()` per request
  untuk request tanpa sesi yang belum terkena 429. Limiter mengurangi volume,
  bukan menghapus query; cache session-tracking bisa menjadi tiket terpisah.
- `bootstrap/app.php` masih memakai pesan 429 Inertia hardcoded
  ("Terlalu banyak pencarian …"). Pesan ini tidak terlihat pada toast global
  (klien memakai `Retry-After` + `lib/http-retry-after.ts`), tetapi menyesatkan
  untuk endpoint non-pencarian bila event tidak dicegat. Di luar satu alasan
  berubah tiket ini.
- `GET /recruitment/track/feedback` dan `GET /track/edit` tidak dibatasi; tiket
  hanya menyebut mutation.
